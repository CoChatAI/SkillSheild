# Learnings: skillshield-secrets-last-launch-plan-20260330-110800

## Phase 1 Learnings

- The repo already has a meaningful split between public edge and scanner runtime, so the release gaps are operational glue rather than missing product surface.
- The queue gap is exact and easy to state: `packages/worker/src/routes/webhooks.ts` enqueues scan jobs, `packages/worker/wrangler.toml` defines only `[[queues.producers]]`, and there is no Worker `queue(...)` handler anywhere under `packages/worker`. Later phases should plan around introducing a consumer path rather than assuming one exists.
- The scanner service itself is more complete than the container story. `packages/scanner/src/index.ts` already exposes `/health`, `/scan`, and `/scrape/:source`, but `packages/scanner/Dockerfile` is still a scaffold that never copies app source or launches the server. The production-container phase should focus on packaging and runtime dependencies, not inventing a new service shape.
- The infrastructure gap is broader than the three stub files suggest. `main.tf` only pins the Terraform version, and there are no provider declarations, variable definitions, queue resources, or outputs checked in. Later infrastructure planning needs to account for foundational Terraform wiring as well as the specific D1/R2/DNS resources.
- `README.md` is useful for later phases because it already names the intended Cloudflare bindings, scanner env vars, and deploy order, but it currently describes a desired operational state that the workflows and Terraform do not yet implement. That mismatch should be treated as a documentation-to-reality gap during rollout planning.

## Phase 2 Learnings

- The cleanest target architecture is not a major reshuffle. `packages/worker` already fits the public-edge role and `packages/scanner` already fits the private execution role, so Phase 2 mainly had to define the missing seam between them: Cloudflare Queue messages consumed by the Worker and forwarded to Fly.
- The repo strongly supports keeping public reads on Cloudflare. The Worker already reads D1 for dashboard data in `packages/worker/src/index.ts`, while the scanner already writes D1 and R2 directly in `packages/scanner/src/db.ts` and `packages/scanner/src/publisher.ts`. That makes D1 and R2 the stable shared state layer rather than something that should move to Fly.
- The reason the scanner stays outside Workers is concrete in code, not theoretical. The scanner uses a Node server (`@hono/node-server`), filesystem cleanup, archive tools, and external command execution, so the later implementation phase should preserve that private container model instead of trying to force the scan path into the Worker runtime.
- There is currently no checked-in Fly config at all, only placeholder GitHub workflows and a scaffold Dockerfile. That means the Fly deployment story is still entirely a repo gap, and later phases need to treat `fly.toml` plus deploy automation as first-class deliverables rather than assuming the host setup already exists.
- The most important sequencing insight is that secret wiring is a narrow final action once the code and config are real. The risky part is not knowing the production tokens; the risky part is leaving operational assets half-defined. Later phases should therefore maximize dry-run-ready artifacts before touching any live credentials.

## Phase 3 Learnings

- The repo already contains the right scan payload shape in practice even though it is not formalized yet. `packages/worker/src/routes/webhooks.ts` and `packages/worker/test/webhooks.test.ts` show the real contract fields that later code should standardize instead of inventing a broader queue envelope.
- The smallest durable contract is one schema shared three ways: producer, consumer, and scanner route. `packages/shared` is already the natural home because it exports Zod schemas and shared types to both runtimes. Keeping a Worker-only queue type and a separate scanner `ScanJobRequest` would create avoidable drift.
- The scanner auth problem is narrower than a full auth system. `packages/scanner/src/index.ts` only needs a private bearer-token gate on mutation endpoints plus a public `/health`, and it can follow the same optional-when-unset pattern already used for Worker webhook auth. That means auth behavior can be fully implemented and tested before any real token exists.
- The production Dockerfile needs to reflect the scanner's actual shelling-out behavior, not just Node packaging. Reading `packages/scanner/src/scanner.ts`, `packages/scanner/src/adapters/clawhub.ts`, and `packages/scanner/src/publisher.ts` made the runtime dependencies concrete: `skill-scanner`, `unzip`, `zip`, and `tar` all need to be present in the final image.
- The main gotcha for later implementation is to keep retries at the queue boundary. If the Worker queue consumer adds its own retry loop on top of Cloudflare Queue retries, diagnosing scanner outages and bad-contract failures will get much harder.

## Phase 4 Learnings

- The Terraform gap is wider than the stub filenames imply. `infrastructure/terraform/` is missing not just D1/R2/DNS bodies, but also provider config, variables, outputs, and any queue resource file at all. Phase 4 therefore had to treat `queues.tf`, `variables.tf`, and `outputs.tf` as release-critical additions, not optional cleanup.
- Resource naming is already fairly locked in by checked-in code. `packages/worker/wrangler.toml`, `packages/shared/src/constants.ts`, and `packages/scanner/src/publisher.ts` all reinforce the same Cloudflare names: `skillshield-db`, `skillshield-skills`, `skillshield-reports`, `skillshield-meta`, and `scan-jobs`. Later phases should preserve those as defaults and avoid inventing a second naming scheme unless there is a migration plan.
- There is still no Fly config anywhere in the repo, so the scanner deployment story is not merely missing secrets; it is missing the app identity and health-check shape entirely. The clean pre-secret deliverable is a checked-in `fly.toml` with app name, internal port, and `/health` checks, leaving only Fly auth and runtime secrets for the cutover phase.
- The full-scrape workflow can be grounded directly in current scanner code instead of an invented operator interface. `packages/scanner/src/index.ts` already defines the useful knobs as query params on `POST /scrape/:source`: `wait`, `limit`, `delayMs`, and `useLlm`. Reusing that shape keeps the operator workflow thin and avoids adding a second orchestration contract.
- One notable config gotcha is the current D1 placeholder in `packages/worker/wrangler.toml`: `database_id = "local-dev-placeholder"`. That is fine for pre-secret validation, but later phases need an explicit environment split so a real production D1 ID can be wired without replacing safe local defaults in the checked-in root config.
## Phase 5 Learnings

- The repo's real secret surface is smaller than the operational surface. In current checked-in code, the Worker only directly consumes `WEBHOOK_SECRET` while the scanner directly consumes Cloudflare D1 and R2 credentials in `packages/scanner/src/publisher.ts`. The rest of the cutover risk comes from wiring planned runtime seams from Phases 3 and 4, especially `SCANNER_SHARED_TOKEN` and deploy credentials, without mixing them into checked-in config.
- One important cutover distinction is between secrets and deploy-time identifiers. Values such as the real D1 database ID, Cloudflare account ID, Fly app hostname, and Worker route are not all secrets, but they still need to be introduced late because they are the account-specific values that convert placeholder config into a live production target. Treating them as part of the final wiring step keeps earlier phases reviewable and repeatable.
- The biggest operational risk is ordering, not syntax. If webhooks are registered before the Worker queue consumer and scanner auth path are both live, SkillShield can accept real webhook traffic and enqueue jobs that have nowhere safe to go. Likewise, running the first full scrape before Worker reads and public report routes are live would populate storage without a finished public verification path.
- Production verification has to exercise the actual seams in this repo, not just health endpoints. For this rollout that means checking: Worker `/health`, scanner `/health`, webhook enqueue behavior in `packages/worker/src/routes/webhooks.ts`, queue-to-scanner delivery once Phase 3 lands, and public asset/report reads through the Worker after the first scrape. A green deploy without those seam checks would miss the real release blockers this plan is addressing.
- The cleanest go-live is a narrow final window: apply account-specific IDs and secrets, deploy scanner, deploy Worker, run one bounded scrape, verify public reads, then register upstream webhooks last. That keeps externally triggered production traffic as the final irreversible action instead of something that can race ahead of the runtime.

## Phase 6 Learnings

- Consolidation exposed that the plan is only internally consistent if the queue-consumer work is treated as the first implementation seam, not just one blocker among several. The current repo already emits `SCAN_QUEUE` jobs from `packages/worker/src/routes/webhooks.ts`, so every later deploy, infra, and cutover step depends on formalizing that contract and consuming it.
- The cleanest final plan for this repo is narrower than a generic launch checklist. Because `packages/scanner/src/index.ts` and the Worker public routes already exist, the missing work is mostly operational wiring around real code paths: consumer config, scanner auth, Docker packaging, Terraform resource ownership, and manual-first workflows.
- The most important final gotcha is that several production values are not secrets but still need to be delayed with the secret-wiring window. The real D1 database ID, Cloudflare account and zone IDs, and the final scanner base URL are the values that turn placeholder-safe config into a live target, so introducing them early would break the intended secrets-last discipline.
- The residual risk profile is now clearer: technical completeness is achievable before credentials, but launch safety still depends on proving the scanner image can run with `skill-scanner` installed and keeping webhook registration as the final irreversible action after bounded production verification.
